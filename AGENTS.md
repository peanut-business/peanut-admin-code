# peanut-admin-code

Peanut Admin Host composition, client delivery and runtime acceptance; official Module author source belongs to the dedicated Module development application, not this Code repository. No private Project dependencies or duplicate kernel.

## Execution discipline

- Start or resume from the current requested result, unfinished work, valid evidence and running handles. Keep one owner for dependent implementation through delivery; delegate only independent work with clear write boundaries. Do not reassign stages, create extra reviewers or replay completed work merely to report progress.
- Before an expensive or mutating command, inspect its actual producer, consumers and recovery entry, registered tools, required edition/configuration, source/lock consistency and exact write set. Distinguish missing capability from unused capability or environment failure; do not discover known prerequisites by repeatedly building or installing.
- Before generation, build, upgrade or cleanup can overwrite existing work, preserve the affected tracked diff, index state, untracked file contents and base revision in a recoverable location. Hashes and path lists alone are not backups. Protect application customizations and never replace current assets with guessed reconstructions.
- Use the native entry for the final admitted module/dependency combination. Read which dependency preparation, API generation, build and compile steps it already performs; do not run those steps again separately or per module unless changed inputs or the actual contract require it. Do not add a competing runner, ledger or gate.
- On failure, retain the actual command, exit code, nested error, completed writes and recovery handle. Inspect supported failed-state forward completion and rollback separately; a rollback backup requirement does not itself forbid forward repair. Fix an evidenced cause before rerunning only the affected step; UNKNOWN or running operations must be reconciled through the same handle, not resubmitted.
- Batch known dependent commands locally with explicit failure propagation; parallelize independent reads, not shared writes. Return to model reasoning at a real decision or error, not after every mechanical command. Use existing tools rather than creating orchestration scripts for this rule.
- Read only the relevant rule and source sections. Summarize large outputs locally; normally return at most 8 KiB of selected fields and failure excerpts, keeping necessary raw evidence outside model context. At a safe milestone, compact to the current result, open issues, evidence paths and precise next action; do not reload full history or unchanged rule bodies without a reason.
- Reuse passed checks while their relevant inputs remain unchanged; report only actual coverage. Choose model and reasoning effort separately for the current uncertainty, use local tools for deterministic work, and escalate only on concrete evidence. Record one result at milestones, finish the authorized scope and stop; these rules add no test, release, deployment or data-operation permission.

Legacy `prepare`/`exec` remain available. Do not change global defaults, copy dependency directories, or treat environment preparation as test/build/release permission. Preserve fixed release source commits and their historical snapshots.

After context compression/summary, model or executor switch, Session recovery, `history_lost`, or loss of certainty about the current task/candidate/write set/loaded routes, reload Project `AGENTS.md` → core → current task route before the next rule-dependent write or expensive validation. Use `tools/quality/README.md` and each affected project's native commands for checks; report the actual source, dependency and validation scope. When reading Code public rule bodies through Project, pass this explicit Code checkout and verified commit with `--application-root` and `--application-ref`; `--content` must return real source text, not a pointer. Do not load entire handbook/API/migration data by default or file self-certified reading receipts. Uncertain rule semantics require evidence and the user's decision; do not weaken security or tests to obtain a pass.

Isolated worktrees; preserve concurrent work; normal validated integration/push to dev, verify remote refs; never force/rewrite history. main, formal publication/deployment, real customer/financial data, paid plans, visibility and license changes require applicable authorization. No private rules, credentials or customer data in public repos.
