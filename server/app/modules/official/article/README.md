# Article Document owner and business Save

Existing Article body owners use official.article.edit for document creation, editor metadata, write tickets and business Save. Add permission alone does not edit an existing owner; ordinary detail still requires official.article.detail. Status permission neither writes a draft nor creates a version.

For an existing unpublished Article with empty legacy HTML, POST official.article.document with id and a stable request_id. Nonempty legacy HTML requires explicit migration; no empty Document replaces it. GET official.article.document.editor?id=… returns the exact owner, current owner_revision, Document state sequence, authorization revision, current content capabilities and any saved binding. Its article_metadata comes from the same locked Article row as owner_revision. The image field is the stable writable file_key (or empty); image_url is a separate display delivery URL and must never be sent as a writable reference. Upload and picker consumers retain FileRecord.file_key rather than deriving a key from a URL.

Solo draft changes use the existing Document save command. Collaborative transport uses the Article owner entry and the public CollaborationTransports::ownerTransport contract. Article rechecks the document and current authorization revision after transport preparation; it does not mint a second business credential. The selected transport must supply the matching owner and publicly allowed WSS configuration. Missing or changed transport fails closed; private control origins are not browser discovery addresses. Actual routes and response fields come from the generated API contract for this version.

POST official.article.document.save with id, document_id, expected_state_seq, owner_revision, stable request_id, cid, title, is_show=0 and supported metadata. Body bytes and client owner fields are forbidden. The original request records the current actor and full input hash, commits before Document freeze/RPC, obtains a committed immutable version, then rechecks current owner authorization and state CAS in a short transaction. That transaction commits metadata, fixed revision/source sequence/snapshot digest, and the completed Save receipt together. Autosave never changes this binding.

An editor keeps the owner_revision loaded with its Article metadata until an explicit reload. A fresh edit-purpose response rechecks current authorization before a new Save and must match that owner baseline and the exact durable Document sequence. Its authorization digest may change with a legitimate durable ACK because the digest includes state_seq; it is not compared to the pre-ACK digest. An admitted unknown request keeps the original key and payload.

After an unknown result, GET official.article.document.operation with the original id and request_id. A prepared request continues by repeating the same Save request and payload with the original person's current authorized session; it does not create a new operation. This also supports solo mode, whose Document operation query is not a collaborative barrier query.

Publication from fixed rich-text versions, anonymous immutable projection and historical conversion are not implemented by this slice. New Save requires unpublished state, publishing a managed body is rejected, and public reads of a managed body return ARTICLE_PUBLIC_FIXED_VERSION_UNAVAILABLE rather than serving draft or old HTML. Legacy unmanaged CRUD remains available. Status-only users may hide a managed Article without changing its fixed binding.

Apply the new incremental migration through the normal Module lifecycle before using these entries. Source and pure contract checks do not prove real database transactions, two-user collaboration, revoke/retry behavior or WSS readiness.
