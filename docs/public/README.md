## 产品开发与定版

**对象必须分清**：脚手架交付 ST/MT 两种薄模板（官方 5.1.10 新建 APP 的 \`modules.lock\` 为空、无模块源码），模块专用应用是官方模块的作者来源。已有固定 ST/MT 测试 APP 安装了 8 个模块，不代表新模板默认捆绑 8 个模块。普通业务 APP 只选自己需要的模块及依赖闭包；安装后的权限、租户和业务数据归 APP/实例所有，不由模板覆盖。

脚手架模板的 ST、MT 是两个独立交付形态；模板创建和升级继续使用 Peanut CLI。仅首次创建产品要求全新的空目录和空数据库，由 CLI `create` 生成源码；`create` 只写入源码，不安装依赖、不建库、不启动服务，也不初始化产品 Git 仓库。之后按生成项目的锁文件准备依赖、开发环境和必要构建，启动并通过安装页面向导完成首次安装，确认访问后同步该产品自己的 Git 仓库，在 `dev` 分支持续开发。

既有产品保留固定目录、专库、Git、配置、上传、安装身份和业务数据。CLI `upgrade` 按旧模板 baseline、当前定制和目标模板做三方比较，审阅并解决冲突后应用同一计划；依赖准备、前端构建和迁移按变化另行处理。它不等于 Git 分支合并或生产更新，不通过重建产品消除冲突。

产品定版环节在开发／发行机器按锁安装前端构建依赖，运行现有 `scripts/deploy-update.sh --prepare-release --version=<产品声明版本>`，将普通 admin、MT platform 静态文件与源码一起提交，经维护者审核合入产品 `main` 并创建 tag。生产首次从固定 `main` 在全新空目录、空库安装，后续在原目录更新固定 Git 提交；只准备 PHP 依赖和配置、应用尚未应用的迁移并确认访问，不要求 Node/npm/pnpm 或再传前端压缩包。PC/H5后置。具体入口和保护见[产品 Git 交付](application-release.md)；源码交付不等于实际安装或更新完成。

### 从业务需求到交付：按变化选择最短路径

| 发生什么变化 | 在哪里开发、验证 | 什么时候发行/更新 |
| --- | --- | --- |
| 只有某个业务 APP 的功能变化 | APP 自己的 dev、真实业务路径和受影响测试；不用修改脚手架 | 业务验收后交付该 APP 的 Git；不重发 Core、模板或模块 |
| 官方模块新增功能或修复 | 模块专用应用开发；本地验证依赖、迁移、接口及直接消费者 | 只发行实际变化的模块版本；消费者按需安装/升级，不整套重装 |
| 脚手架装配、创建或升级机制变化 | Code dev；先验证本地原生双 Edition 创建、必要安装和升级行为，再固定来源 | 仅确有通用变更才单独发行模板；有破坏性变更按约定执行一次全 CI |
| PHP/Web Core 公共技术能力变化 | 对应 Core 作者仓；本地联调当前直接消费者 | 真有变化的 Core 先独立发行，Code/模块/APP 再选择采用；不随模板例行重发 |
| 只有说明、任务分工、普通文档变化 | 文档引用、事实和相关语法检查；无需新建 APP 或连接数据库 | 随对应开发仓 Git 交付，不触发制包或完整 CI |
| 已有 APP 升级脚手架/模块 | 先只读 plan 和三方冲突决策，保留 APP 自有数据；按变化补依赖、生成 API/前端并验收 | 这是消费者采用，不再发行上游；只有业务 APP 自身需要发布时才交付其版本 |
| 实例上线、迁移和部署 | 使用已定版 APP、原生迁移/运行检查、真实浏览器验收和恢复合同 | 单独的部署/运维动作，不因上游版本出现就自动操作 |

同一批输入已经通过的检查直接复用；本地开发先发现和修正问题，再固定候选。CI 是正式制品生产与必要资格验证，不是开发试错环境。创建源码、首次安装、源码升级、模块采用、应用发行、实例部署分别报告，不把上一环节的 PASS 当成下一环节完成。工作完成条件取当次用户目标，而不是工具或子任务自行“停止”。

完整使用手册阅读同一APP来源版本，不把开发分支的新说明当作旧实例已经具备的能力。既有包和更新器保留其实际消费者与技术合同，B 包、`peanut package`、`release/apps` 不再列为日常生产步骤。
