## 固定开发库的 File adopted 来源承接

`schema:application --scope=source-development --file-adoption-relocation=<受保护输入>` 仅显式选择 `database/maintenance/20261024-relocate-file-adoption.sql`；它不进入 seed、默认应用 Migration 或 HTTP 路径。该固定项只承接已知 File adopted key 及原 provenance 摘要，从原开发库／原运行根到已核目标。原 proof、admission、SQL、账本及业务数据不改写；同一 MySQL UUID 本身不是承接授权。

输入采用 `peanut.file-adoption-relocation-input.v1`，显式声明维护 key／SQL 摘要、原 proof 摘要、source_root、target_root、完整 target_instance、原搬迁 receipt／dump 的路径及摘要、有效期限和实际审查引用；输入、计划、备份与原安装锚点按现有私有文件权限及原生 lease 校验。现有 Host → ThinkPHP Migrator → Adapter 执行单一固定断言，completion 先独占创建并 fsync 私有承接凭据和目录，官方 `migrated()` 才能写新维护 marker 的 applied。消费者要求两者完整匹配，继续验证旧 evidence／admission 及当前 File postconditions；维护时业务行摘要只证明执行前后保全，不冻结以后正常业务写入。

失败后沿原 `snapshot-failure`／`restore-failure` 显式选择同一固定项。专用 profile 仅在原快照、完整其余账本、锚点及当前 File 数据仍匹配时，事务撤销本次原先不存在且完整失败行匹配的新 marker；新凭据原字节只移入固定隔离路径，不删除、不重编码。两媒体中断保持 fail closed，仅允许同一不可变 capsule 的精确 afterimage 显式对账，不自动重试或手标成功；有效 applied＋凭据、later-use 或未知状态均拒绝失败恢复。`applying` 硬中断不属于此 failed profile 的恢复范围，保持拒绝，未取得全中断恢复资格。完整 SQL 快照属于灾难恢复材料，不是这一窄恢复的替代入口；恢复承接还必须配套私有凭据、原计划／输入与安装锚点，代码本身不能恢复历史数据。

维护者在现有 MySQL 服务分配尚不存在的应用空库，可登记 `resources.schema_allocations` 中唯一 `peanut.schema-allocation.v1` operation，再以 `scripts/project-resource-lease claim` 的正常 owner/thread/candidate/gate 参数及 `--schema-allocation <ID>` 取得封闭资源，运行 `schema-allocate --lease <ID> --owner <实际线程>`。不接受调用者资源或 SQL；普通 APP 不依赖维护者 Project。只创建登记的同名专用库、账号及十项既定库级权限；应用结构、初始化和数据迁移仍走已有 Migration／安装入口。

operation 完整字段为 `stable_resource_id/protocol/owner/thread/tool_source/lease_gate/database_resource_id/endpoint_id/server_uuid/version/account_host/credentials/transport/receipt_root/php_executable/max_seconds/paired_operations`。`paired_operations` 是两个不同 operation ID 按字典序排列的数组，两项登记使用同一数组、owner、源码、物理服务、UUID、version、Host、transport 和期限；仅通过首项 ID resolve／claim／execute，第二项不单独执行。`tool_source` 固定干净源码的 `root/common_dir/commit/files`（两执行脚本与 registry resolver 的 SHA-256）；`credentials` 仅引用 0600 dotenv 的 `path/sha256`，内容严格为 `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASS`，密码为 32–128 位 URL-safe 字符，不能空。`transport` 字段是 `ssh_command/ssh_alias/docker_command/container_name/mysql_command`，root 密码仅在远端容器展开。`receipt_root` 为登记备份根内按 operation ID 固定的私有叶子；`max_seconds` 为整对操作共用的 60–300 秒。database 的 endpoint、schema policy、lease gate、username、account_host、凭据引用及精确十项权限须一致，无 GRANT OPTION。

本地开发／测试新账号按当前合法中央登记显式采用 `account_host="%"`，operation 与对应 database 的值必须相同；不从未知 Host 或连接失败 fallback。分配器保留原有 `environments == ["development"]` 边界，通配目标还要求 `application_runtime=false`；环境和策略来自 resolver 验证的 Project 当前登记，不接受调用者另传标记、任意登记文件或资源来把生产伪装成本地。真实 endpoint、物理服务、UUID／版本、schema scope、凭据及传输仍须匹配登记。生产或其他环境不自动放宽，既有明确固定 IP 登记仍要求 canonical IP；不修改已有账号、root、其他 schema 或共享数据库服务。专用用户名必须与目标库同名且不能为 root，仍用非空密码及本库十项权限，无 GRANT OPTION。

`USER()` 表示本次真实连接来源，`CURRENT_USER()` 表示实际匹配的授权账号。原 APP 普通 PDO 观察继续验证真实 principal、UUID／version、连通性并保留来源／路由证据；对 `%` 策略不再要求来源后缀等于 `%` 或某固定 IP，不把旧来源证据改写成授权 Host。固定 IP 策略仍按原合法来源合同核对。新账号普通登录必须匹配专用 `user@<登记account_host>`（通配为 `user@%`），同时记录独立的真实 `USER()` 来源；分配器不代为取得原 APP 的前置观察。配对 scope 和账号锁使用登记 Host 原值，首次两目标任意 Host 同名账号缺席检查、逐项 UNKNOWN／后像及终态释放合同均保持。

分配正常同时持有两目标 `mysql-schema` 完整 DDL 声明、两个精确 `mysql-account=<endpoint>/<user>@<host>` 锁及输出目录，不取得服务启停锁。首次 DDL 前在这一 scope 内一次观察两 schema 和同用户名任意 Host 的账号均不存在，并将两目标、lease、registry 摘要、UUID／版本及观察时间持久绑定在首项 operation 的私有 journal。任一对象存在即返回未写入的 `EXISTING_RECONCILIATION_REQUIRED`，不修改它们。随后逐项仅复查本项目标，第二项不要求第一项已创建的 schema 仍不存在。字典序固定唯一 journal 入口，避免从另一项或倒序重放。入口核 UUID／版本、完整管理可见性及无 mandatory roles；每项目标成功需完整空对象清单、精确直接权限及普通 PHP PDO 登录身份。副作用前逐项先持久记 UNKNOWN；完成第一项后第二项遇到存在对象、部分执行、断连或写入不明均保留总 UNKNOWN 及两目标边界，不重发、自动释放或过期清理。两项均 COMPLETED 或整对未写入的 EXISTING 可由原 owner 在进程终止后正常释放；确凿零派发的 preflight UNKNOWN 仅走下述独立终态对账。journal 始终保留。它是顺序 DDL，无跨库事务或自动回滚承诺。

管理权限按 `mysql.user` 原生静态全局权限列校验，不依赖 `SHOW GRANTS` 的 `ALL PRIVILEGES` 字面形式。[MySQL 8.4 官方说明](https://dev.mysql.com/doc/refman/8.4/en/show-grants.html)明确全局权限会逐项展开，动态权限／PROXY 可单列。分配器要求同一 UUID／版本、`root@localhost`、无 mandatory roles，直接具备目标十项权限、CREATE USER 和全局 Grant_priv=Y；全局 SELECT 同时支持 schema／账号完整可见性。按 [partial revoke 原生表示](https://dev.mysql.com/doc/refman/8.4/en/partial-revokes.html)检查 User_attributes.Restrictions，拒绝目标库所需权限或 mysql.SELECT 被限制、未知结构及矛盾状态。合法 ALL／逐项表示对应同一权限列，不为适应输出向 root 增权，也不接受角色／子串代证。

零派发 preflight UNKNOWN 的正常收口分两阶段。先保留原 schema_allocations／旧 tool_source／journal／lease，原 Project writer 只提交 `resources/operations/schema-allocation/<原lease>-terminal-review.json`。独立 review 采用 `protocol=peanut.schema-allocation-zero-mutation-review.v1`、`verdict=RELEASE_ZERO_MUTATION`，绑定原 lease／owner／operation、metadata_sha256、resources_sha256、journal_path／journal_sha256、marker_sha256、原 registry_commit、实际独审 reviewer_thread／reviewed_at、新 reconciler_source（三工具 root/common_dir/commit/files），以及 `local_process_terminal/remote_process_terminal/zero_mutation_source_review=true`。`readonly_evidence`、`execution_evidence` 均为实际原件的 path／sha256；`readonly_counts` 按原两个 operation ID 指明 database／username 及只读结果中的 schema_count_key／account_count_key，不编造查询结果。独审须确认已审原源码在每个实际写入派发前先持久设置 mutation_dispatched，且本次无远端未明写入。

原 owner 在新固定管理树执行 `scripts/project-resource-lease schema-allocation-reconcile --lease <原lease> --owner <原owner>`。命令在原生 mutex 内以原 registry Git 内容／摘要重建完整原 pair 资源，核旧／新固定源码、原 owner、原物理锁和 PID／birth 终止；原 journal 必须精确 UNKNOWN、整对及两 target 均 mutation_dispatched=false／PREFLIGHT，且无 pair_precheck／current_operation。独立只读原件须在该失败后同原 lease 核 UUID／version／principal、两 schema 与两 username 任意 Host 均缺席，并有执行终态原件。到期不授予执行权，也不妨碍这一严格终态核验。工具产生 `<原lease>-terminal.json`，保留原 UNKNOWN journal 原字节，经同一正常 release 收口原 marker／lease／锁；原 receipt 可对账，禁止删／手改 journal、改成 EXISTING 或放行部分写入。prune 继续保护 schema allocation，不能代替 owner 对账。

terminal 先在原目录写完整临时文件并 fsync，在已持原生 mutex／输出边界内检查目标不存在后原子发布、fsync 目录；不写半截最终文件。发布的 intent 绑定原 metadata/resources 原字节、原锁目录 device/inode、版本化 review 及 producer。释放中断时，相同命令可据这一已发布且全字段复核的 intent 继续清理已缺席／部分清理的精确原 inode，拒绝替换锁、额外锁及新 holder；不重建原 proof。marker／metadata 部分退出或已完整退出也可对同一 receipt 继续对账，不扩大为一般 UNKNOWN 清理。

已派发写入但原进程终止、双目标实际成功的 UNKNOWN，复用同一 review 路径、`schema-allocation-reconcile` 命令和原 scope／锁／producer／原子 terminal 释放机制，独立走完成采纳分支。review 使用已有 `peanut.schema-allocation.v1`，`verdict=ADOPT_COMPLETED_PAIR`，`completed_afterimages_source_review=true`，不声明零写入；原身份与摘要字段不变。`readonly_evidence` 绑定原 lease 下双目标计数原件（`actual`、`at_utc`、原 journal 摘要），每库／同名账号计数须为1；`execution_evidence` 绑定原写入执行终态。`completion_evidence` 按两个 operation ID 指定 `{"source":"original-journal"}`（仅原目标已 COMPLETED）或独立原件 path／sha256（同 lease、原 journal 摘要、失败后 root 后像及普通登录成功）。逐目标核空 schema／账号、UUID／version／root 可见性、十项精确直接权限／无 Grant Option 与普通 user@Host 登录；外部 SHOW GRANTS 复用分配器原权限解析，不靠成功布尔值。原 pair_precheck 必须整对缺席，原两 target 均已派发且仅为 COMPLETED／UNKNOWN，最后同步调用成功、原进程及远端写入已终止。terminal 记录 `PAIR_COMPLETION_ADOPTED` 和核验后像，原 UNKNOWN journal 原字节／失败预算保留；缺任一成功证明仍拒绝，不把未知部分写入视为完成。writer 只需正常版本化独审 review，原 owner 收口后继续业务；不改原 allocation source／retry_of、不新建库或账号、不再发 DDL、不取得重试或新执行权。

原 lease 安全释放后，writer 再把两 operation 的 tool_source 更新为同一 terminal producer 新固定源，增加相同可选 `retry_of={"path": "<原terminal receipt绝对路径>", "sha256": "<实际摘要>"}`，其余任务／目标合同不变。正常新 claim 必须使用未退役的不同 lease ID、同一原 operation／pair；producer 复核原 review 在 Project 历史中的版本化字节、producer 三工具源码、原 registry 和完整 scope 闭包、内嵌 journal 与旧原件一致及旧边界确已退出，拒绝形似回执的自报 JSON。新 journal 命名为 `schema-allocation-<新lease>.json` 并记录 retry_of，不覆盖旧 journal，也不重置原任务失败预算。新执行重新完成全部权限／配对缺席／账号登录等前置，不把终态 receipt 当执行 permit。这一顺序避免先改 source 使旧 UNKNOWN 无法收口。

活动 MySQL scope 可跨登记摘要比较。原生普通 claim 绑定 canonical 登记原字节和摘要，并未要求旧登记必须有 Git 提交。旧字节先取当前合法 resolver 所定位的同一逻辑 Project 主目录固定 `resources/project-resources.json` 保留内容，核 canonical、普通单链接文件、实际用户所有权、不可组／全局写及当前仓库映射；摘要不匹配时再从该 Project 已提交祖先查找精确原字节。两种来源都须匹配原 native proof 摘要、project identity／authority。旧字节只解释原 holder 边界，不授权新 claim；对应 database 的安全投影（schema／namespace、端点、凭据引用、物理身份／别名、版本／UUID、gate、访问及租约策略等）、真实 Git candidate 和完整原锁须与当前合法 authority 核对。其余登记项及用途说明变化不强绑整份摘要；不将不同库的清单版本差异当作实际 schema 冲突。来源缺失、相关策略／身份变化及真实 schema／table 冲突仍拒绝。调用者不能指定旧文件路径，松散 snapshot 或外部 proof 自报不能单独放行；工具不改外部 lease／proof／续租。本入口不更改服务管理、旧 UNKNOWN 或 registry rebind 规则，采用新管理源及必填 pair 字段须由原 registry writer 正常登记。

直接 CLI 的 `migrate:run preflight|apply|verify` 使用与 `schema:application` 相同的参数、实例上下文和准入；`migrate:status` 委托该入口的 preflight，不创建迁移表，输出真实 text key。源码开发需要原有 `--scope=source-development` 和实际 owner／thread／session／gate、维护及恢复证据；发行升级仍走安装实例的正式升级入口。官方通用的目录扫描执行、`--date`、rollback、breakpoint 和 seed 命令不注册，不能绕过生命周期保护。模块仍通过 `plugin:install`／`plugin:upgrade`／受控 `plugin:reconcile` 进入同一官方执行器，不由应用 schema 命令接管其业务语义。

首次安装自动按已选择 Module 的依赖图执行；官方／发行批量 reconcile 将锁定 Module 依赖映射到所属 Plugin，使用同一原生依赖排序后执行整个包。只读发行计划先核同一执行图，报告的选择列表保留规范 key 顺序；缺失依赖、依赖环或未选择的必需依赖在执行前拒绝，已停用包不被隐式启用。Article 声明的 Document 依赖会先完成真实生命周期；Article 仍核 Document active、两条真实 applied stage 及应用前置证明。用户无需手工调整安装顺序，排序不代替任何账本或业务后态保护。

源码开发 preflight 按真实 pending 顺序列出逐条来源、前置证明和后继依赖；缺少业务终态保全或完整恢复覆盖时，计划仍不授予执行权限。原仅覆盖模块迁移来源字段的两账本恢复合同不能用于包含菜单、权限、通知或认证数据变化的链。已迁移归属的 File 应用历史，只在原不可变 SQL、现行 canonical adoption 声明和原账本 key／checksum／applied 一致时识别为历史保留；不删除原行、不把它记入模块账本、不以历史记录代替当前 File 数据证明。未知额外历史继续拒绝。

源码阶段账本按原有序链核对已完成前缀、当前 applying 与尚未执行项，逐条使用 SQL 真实发行身份；旧历史的完整原行保持不变。源码 apply 只接受现有九条固定 SQL 中由原生账本算出的有序 pending 和精确摘要；维护窗口、原生完整备份、恢复引用、baseline 与完整表并集必须一致，旧两账本证据不能扩大使用。维护证据必须证明 HTTP、worker 和其他受影响 writer 的实际排除，且窗口开始不晚于真实备份开始；租约或 JSON 的声明本身不证明外部进程已停止。完整原结构／数据 payload、原生终态 rc0、manifest 与 RESTORE 摘要仍逐次核对，不自动恢复。

备份范围复用固定表映射，不由 SQL 解析或调用者清单扩展。首次 applying 前核对完整原 scope；后继不再拿链初元数据否定前序合法 DDL，而按当前真实前态、旧账本和有序完成前缀逐条检查。固定 DML（含唯一应用账本）按实际事件、更新列及派生更新列检查触发器和入向级联；未知写入在对应阶段前拒绝，已完成前缀和失败证据保留。纯 DDL 的业务表触发器不会因存在而一概阻塞。完整元数据可见性必须由当前 PDO 的直接全局 SELECT／本库 TRIGGER 且无部分撤权，或下述显式原生源码观察器证明；不自动授予权限。成功结果仅在原生 applied 后读回真实阶段账本并绑定原 source／DB／window、备份引用和安全 after 结果；它是当次窗口证据，不是当前状态健康核对、跨进程私态重算或完整资格通过。

源码 `schema:application`／`migrate:run` 和 `plugin:install|upgrade --scope=source-development` 可显式选择 `--metadata-tool=<已登记tooling资源ID>`。它使用同一 `SourceApplicationBackup` 固定 SSH/Docker reader，普通 PDO 不换账号，root 密钥只在原容器内展开。原生租约须同时包含该 `tooling-resource-id`、当前真实 owner/thread/Session/source/DB 身份及 `output-dir=<server>/private/installation/source-development/effect-metadata`，并覆盖全部现存目标表的整表读取；实际写入仍要求原 DDL／exclusive 准入、维护窗口和备份恢复。工具的 `source_schema_backup` 必须精确绑定本库资源、库名、MySQL版本及允许表集，不能借用另一库工具。计划固定选择的工具 ID 和登记摘要；backup/apply 使用同一选择，receipt-only 验证不调用观察器。每次 scope 重验及插件 SQL 前后重新读取本阶段元数据，证明远端 UUID／版本、完整权限、nonce、终态回执及精确表集，保留跨库入向 FK 和目标 trigger；普通 PDO 的当前 SHOW CREATE／自增同时匹配，原不存在表显式保留。观察器不接受外来 JSON、任意 SQL 或调用者补造的“可见”标志，不自动接受未知 trigger／范围外级联，也不执行迁移或恢复。原生请求与终态回执存于上述实例私有目录，计划只公开安全 scope／工具及客户端摘要；这些观察不等于备份、业务保全或资格通过。

源码完整应用链的 preflight/apply/verify 在初始化 PDO 前核业务读取闭包：原十一表之外，还需整表读取 `pa_platform_role_permission`、`pa_resource_operation_permission`、`pa_resource_operation_target_type`，供权限证明检查关联保全。十四表读取不扩大十一表备份范围或恢复写集；receipt-only 仍只要求应用账本读取。原生完整 DDL／exclusive 准入覆盖这些读取；普通 read/transaction 声明必须覆盖对应表全部行，缺表、行子集或另一 schema 均拒绝，不能用元数据观察成功替代业务行读取准入。

菜单三条固定应用 SQL 的业务事实由 Identity 的 `MenuSchemaMigrationProof::before(PDO,migration)`／`after(PDO,privateBefore)` 提供。preflight 只公开 `safe_summary`；当前 pending 前驱未完成时列为 deferred，不构造影子菜单、解析 UPDATE 或预测 UUID／自增分配。源码维护 Host 和发行 `update-database.php` 均在原同 PDO 的执行回调内重新取得有限私有 facts，原 SQL 排空后、官方唯一 applied 写入前核 `business_postconditions_verified=true`，随后释放 private_state；它不进入计划、结果或日志。后继步骤以当前真实状态重新捕获，不用链初摘要否定后续合法变更。定制／歧义目录按原 SQL 的采用、跳过和冲突分支处理，不增加整个迁移的拒绝 Gate。

权限三条固定应用 SQL 由 Identity 的 `PermissionSchemaMigrationProof::before(PDO,migration)`／`after(PDO,privateBefore,executionBounds)` 证明。preflight 只公开 `safe_summary`，部门迁移尚有 pending 菜单结构前驱时明确 deferred；Host 不再投影权限 CHECK、提取 SQL 选择器或预测最终行。两个原生直接消费者在同 PDO 的 before 回调重新捕获私有事实，readiness／department 严格返回 `true` 请求原不可变 SQL 整批执行两侧的原生时钟，SQL 排空后、唯一 applied 写入前交给 Identity 校验真实 UTC 毫秒区间及业务保全。platform-ops 不请求时钟，时间字段仍须保持；私有事实只驻留当前阶段回调，后继重新捕获，不进入计划、结果或日志。

菜单／权限回调业务断言不替代真实私有备份及完整结构／数据恢复。断言失败沿官方执行器保留 failed／已完成阶段与原恢复点，不伪回滚 DDL、不自动重放或伪造 applied。安全结果仅记录 id／hash／readonly、具体成功字段、安全计数及原生整批 SQL 的两点 UTC 毫秒／历史连接标识，不保留业务行或私有候选，不能重建原私有前态；涉及这些阶段的独立 verify／已完成 migrate 重放当前分别拒绝 `APPLICATION_SCHEMA_MENU_LIVE_REVERIFY_REQUIRED`／`APPLICATION_SCHEMA_PERMISSION_LIVE_REVERIFY_REQUIRED`，不以旧成功摘要冒充实时保全复验。固定 provenance 执行前按真实结构区分 before_additions／exact_noop；源码 Host 与正式 `update-database.php` 均在该阶段完成回调、唯一 applied 写入之前复用原生证明要求 exact_noop，不能等整条 runner 结束才发现后态不完整。原源码身份、原生权限、完整恢复覆盖与发布资格保持独立约束。

`schema:application verify-receipt --scope=source-development --result=<原native结果>` 单独核“原接受证据”，不是上述实时保全重算。新观测仍需当次实际 owner/thread/session/gate 和正常原生读取准入，在数据库初始化前核完整 `pa_schema_migration` 只读范围；不借用已过期的原 writer 租约。结果只接受原 native writer 的 `private/installation/application-schema/source-development/result-<32hex>.json`，核目录／文件 owner、0700／0600、无链接和文档完整性，单独自报 digest 或任意路径 JSON 不算 writer 来源。原 apply 在真实 applied 回读后、原锁内封存计划路径／字节摘要、原 request／观察时刻、所属合同源码摘要、真实 native executionBounds 及原窗口／备份／有序台账引用；不补造旧收据缺失的字段。

复验绑定原 Git commit/tree、物理 DB／登记资源、原计划 baseline、原时间有效的维护窗口及其原生 dump／终态 process／RESTORE 全链，再在当前只读快照核原选定台账行和原 after 安全字段。原租约现在过期不会抹掉历史成功，当前合法业务定制、grant／revision／时间变化和原 scope 外后续迁移台账追加不要求与旧后态永久相等。合同算法或备份引用字节已变化／丢失、未知来源或未受验收据继续拒绝；不切换工具版本、不复制私有事实或恢复临时数据库来合成证明。输出明确 `verification_level=accepted_original_window_receipt`、`original_window_receipt_verified=true`，同时 `original_private_algorithm_recomputed=false`、`current_target_verified=false`、`qualification=not_run`；它只证明原接受记录及其绑定，不证明当前业务末态、重新计算私有保全或恢复资格。

应用迁移存在唯一 failed、其前仅有连续成功前缀时，可用 `schema:application snapshot-failure --scope=source-development --plan=<原apply计划> --backup-tool=<已登记工具> --backup-output=<新的精确租约目录>`，并提供实际 owner/thread/session/gate 与原计划选择的 metadata-tool。它在当前干净源码、正常 DDL／exclusive 准入、产品锁及同一 PDO schema 锁内，只读取原 pending 全表范围的真实 failed afterimage；不会调用迁移 runner、删改 failed 行、执行恢复或重放 SQL。原计划及其前态备份必须完整，数据库、资源、登记、原安装身份、执行 owner 和固定 SQL 必须匹配；原源码／环境摘要与本次新源码／租约环境分别保存，不重写历史输入。现有账本必须恰好为原历史加连续 applied 前缀及唯一 failed；逐行校验固定摘要、版本、完成时间及错误状态，其后 pending 仍未运行，原历史及账本结构摘要不变。输出使用独立的 `peanut.source-application-failure-snapshot.v1`／`peanut.source-application-failure-reference.v1` 协议，私有记录保留真实成功前缀、failed 行、完整账本、原计划／备份引用与原生 dump 终态；正常 apply 不接受它作为前态恢复材料。恢复仍需单独审阅精确对象、外部 FK／trigger、当前停写窗口和正常执行准入，取证成功不代表已恢复。

失败恢复是独立显式操作：`schema:application restore-failure --scope=source-development --plan=<原生失败backup.json> --maintenance=<当前恢复窗口> --backup-tool=<同一登记工具> --backup-output=<新的精确租约输出根>`，并提供实际 owner/thread/session/gate 和同一 metadata-tool；不传正常 apply 的 recovery 参数。保留原 SMS postimage／空成功前缀和 menu-stable-identities 分配器错误／SMS、group-default-navigation 前缀两个封闭 profile。默认导航分组阶段，以及其后 auth-client、readiness、department、platform-ops、seeded-parent、provenance 六阶段，各有固定累计前缀 profile；分组自身失败仅恢复 SMS 成功前缀与本阶段的四表并集，不伪造菜单稳定标识阶段已执行，要求唯一真实 failed、有序连续成功前缀和全部固定 SQL 摘要；不接受调用者指定表或 SQL。所有 profile 仍要求通知日志前后为空；applying、断连 UNKNOWN、无 failed 的整链后验失败须先对账，不能伪造 failed 进入恢复。历史计划／原备份／失败 capsule 的来源及完整 native receipts 仍核验，当前干净源码／DDL准入与历史源码分别绑定。窗口使用 `peanut.source-development-failure-maintenance.v1`，绑定当前 source/database/authority/registry、failure_snapshot、对应 profile 的固定 write_tables、原完整 read_tables、时间和实际排除 http/workers/other-writers 的私有回执；登记工具或 JSON 声明本身不授予恢复权限。

SMS profile 只恢复 `pa_notice_log`、`pa_schema_migration`；menu profile 还恢复 `pa_menu_definition`、`pa_system_menu`。后六 profile 的可能写集取固定迁移至失败阶段的累计表集，实际差异必须是其子集。无入向引用的表沿用原始 DROP／CREATE／逐行 INSERT 字节；被引用的 permission／role／tenant 保留所有原 ID，只恢复固定非键列，permission 仅可删除原件不存在的新增 readiness 行；session 业务行及分配器必须不变，只还原指定 client CHECK 的原定义或不存在状态。先恢复子绑定，再处理新增 permission，账本最后恢复；恢复原分配器，拒绝未知列、丢失原身份或其他新增父行。新原计划和失败 capsule 同时记录三张只读权限绑定表的全行摘要，恢复前后均须一致。固定 MySQL8.4 dump 消费者完整扫描会话和表字节，原件不修改；派生材料记录原 payload、各原字节段和自身摘要。FK／unique 始终开启；目标 trigger、跨库入向、未知出向依赖和 permission 删除级联拒绝。仅放行固定且前后未变的本库父依赖，包括 role_permission／session 原有的 account、tenant_member 外部父边；它们不在恢复写集内。保留父表的键列不改，不以关闭约束扩大恢复。

恢复还消费原计划已绑定的维护窗口原文件和回执摘要，核原 source/database/authority/registry、pending/selected/baseline/scope 与排除 http/workers/other-writers 的合同。原备份起止、成功前缀及 failed 行的严格 UTC 起止、失败 capsule 起止必须依序处于该原声明窗口内；原源码至 capsule、至当前源码均须为祖先关系，固定 SQL 不变。窗口及回执加入持续文件保护；缺失、时间缺口或已知重新开放／冲突写入均不能以事后声明补证。历史窗口只证明原声明合同，不证明物理全局独占，也不要求已释放的原租约继续有效；当前恢复仍须新的真实租约和窗口。

恢复前在同一正常产品／schema锁和窗口内重新采集完整 afterimage，必须与失败 capsule 的原生 dump 字节完全一致；原两个 profile 仍要求恰好对应两张或四张表变化，后六 profile 允许固定累计写集的变化子集，其余表原字节一致。固定原生 mysql 显式使用 `--skip-reconnect`，从已核摘要且持有文件句柄的私有派生 stdin 执行，密钥仍只在原容器内展开。恢复后验证原账本／空通知日志及完整 scope，并另采原生 postimage；完整 dump 必须与原前态逐字节相同，才能封存 `peanut.source-development-failure-restoration.v1`。前后取证、派生 SQL、终态和原恢复点都保留；postimage 使用独立 restoration snapshot/reference 协议，不作为正常 apply 的前态备份。非零、超时、未知或后验不符均停在真实阶段，不自动重放、运行迁移或开放写入。源码合同及字面值派生检查不代替真实 MySQL 恢复资格，DDL 也不受 DML 事务整体回滚保护。

`plugin:upgrade`／`plugin:install` 的 `--scope=source-development --dry-run` 为明确选择的单个插件生成原生计划，同时必须提供实际 `--owner`／`--thread`／`--session`／`--gate`。入口在初始化数据库前核对干净源码、原安装标记和当前原生资源租约，并在真实产品文件锁、应用迁移 advisory lock 与插件原生锁内读取；缺少真实来源字段迁移时只列为应用前置项。计划和 capture 固定 `execution_admitted=false`，不冒充应用 schema 或发行升级。

同一源码插件入口移除 `--dry-run` 后必须另外提供受保护的 `--source-plan`、`--maintenance`、`--recovery`，不同时执行 backup。宿主要求真实 DDL 原生准入，在上述三个原生锁仍持有时重算完整计划、固定 SQL 闭包和原表范围，逐字段匹配原计划，再核当前有效窗口与真实 native dump／终态 process receipts／RESTORE 合同及独立 Notification 原文件字节。maintenance 使用 `peanut.source-plugin-maintenance.v1`，绑定 source/database/authority/registry、完整 pending/selected、baseline 摘要、完整受影响范围 scope.affected_tables、有效时间和原排除 writer 回执；scope.tables 仅列原来存在的表，scope.absent_original_tables 仅列原来缺失的表，三个集合各自无重复，present／absent 不交且并集精确等于 affected，并与 scope.objects 的存在标记一致。dump／recovery 严格只取 present（scope.tables）；absent 不进入 dump，也不授予删表权限。它仍是运维排除的证明入口，JSON 声明或 advisory lock 本身不证明外部 writer 已停止。capture 必须始于该窗口内。执行前还要求当前 PDO 对完整元数据有直接 SELECT/TRIGGER 可见性；未知触发器和范围外级联写入阻止对应操作，不自动扩张备份。

开发源的纯 catalog 升级可显式使用 `plugin:upgrade <首个key> --source-batch=<有序逗号分隔keys> --scope=source-development`，沿用相同 actor、metadata-tool 与实际租约。只接受原生 `reconcilePlan` 完整准入且 `pending=[]`、无新迁移/adopt/前置迁移或文件副作用的已安装目标；原生 `planned_unchanged` 跳过写入和备份。先 `--dry-run` 形成完整并集计划，再以该计划、真实事前窗口及 backup-tool/output 做一次 `--dry-run` capture，最后用 captured 计划、maintenance/recovery 去掉 dry-run 执行。批次使用独立 `peanut.source-plugin-batch-{maintenance,recovery,backup,restore-instructions}.v1` 协议，旧单插件备份不能代用。

批次持续持有产品、schema 和全部目标的原生锁；写边界仍复核动态 actor/lease/数据库/源和每步原生计划。capture 起止核完整原生 scope、所有主键有序行的 NULL/二进制安全摘要、原始建表语句及分配器；各步完成后保存完整 afterimage，精确连接下一步 beforeimage。不可变 execution、prepared、started、原生 result、completed-prefix 与最终 result 逐份持久引用；commit 后缺 result/prefix 或任何未知均停止，不能重新启动命令自动续步。进程时序单独记录 guard、native process 和整体阶段，不能把含准入的耗时称为纯 dump 耗时。

恢复单位仅为本批起点的完整并集，不承诺保留本批已完成前缀的单步回退；RESTORE 仍为显式人工合同而非自动恢复器。持续排除共享 catalog 全表的所有 writer 是恢复前提，重新开放 writer、租约/窗口失效、外部写入、归属不明或 afterimage 未证明后拒绝旧整表恢复；不相关业务数据、队列、日志和此前批次不回退。开始批次前已完成的操作不追认进新恢复点。

仅当前同一进程、同一命令上下文和 master PDO 内的宿主能力允许原 PLS 执行安装或升级；开始 lifecycle、每段迁移及其原 after／applied 边界、catalog 和失败标记都复核 source/actor/lease/window/backup，原事务提交前和业务 before 完成后的 SQL 执行前再次复核。执行仍由原 PLS 和模块自己的保全合同完成，不复制 SQL executor，不伪造安装或发行升级身份。Identity 的九条固定 DDL 使用同一 stageLedger／before／原 SQL／after／applied 回调：六条 bare CREATE 要求真实目标原缺失及创建后空表；部门与审计表只接受原 SQL 的追加列／索引和合法 no-op，保留原列行值摘要、其余列／索引／CHECK／FK及分配器，核新增字段为规定默认值或 NULL。它不把已有表冒作历史执行，不修改 SQL 摘要，源码与正式更新器共用同一 PLS 合同。原未知 SQL、namespace、append-only 修复和 File 采用身份限制保留。失败保留已提交前缀和实际失败现场，不自动重放、回滚或 restore；这些后态断言不替代具体失败恢复入口或真实 MySQL 恢复资格。

Notification forward／File adopt 的只读 source 计划在原所属业务报告通过后，可明确表达 `planning_complete=true`、`source_admission_deferred=true`，同时仍保持 `may_apply=false`、`execution_admitted=false`；`source-plugin-plan` 只来自当前真实 host/PDO/原生锁的读取区间，永不由实际写入准入方法返回。这样可以先计算精确恢复闭包，不能据此写入。实际 apply 先验证原计划、真实原备份和有效窗口，取得真实进程内能力后，在同一插件锁内重做原生计划，要求这次真正 `may_apply=true`、固定 effects／原范围／旧 ledger 未变，再进入原 PLS。admission 分别绑定原 deferred 计划和这次可执行计划的摘要；原 File 后态、历史应用记录、安装身份、原 Notification 前后态及所有未知/失败 Gate 仍由原合同判断，不为本地开发伪造已安装或 applied。

source File adopt 的原记录沿用唯一原生 module ledger 和原 provenance；其 `source-plugin` admission 按原 source/DB/operation/request、备份窗口引用和内容摘要解释为历史原生准入记录，供原 adopted readback 验证。这个内容摘要不是发布者认证，不授予未来写入权限，也不是跨进程重新计算私有保全事实；新的写入仍须重新持有实际 native 能力。其他安装／server-release admission 规则不变。

`peanut.source-plugin-result.v1` 在原所属 after 实际通过、原 PLS 返回并回读真实 applied ledger 后，封存到 `private/installation/plugin-source-development/result-<32hex>.json`。它保存真实回调顺序的 key／SQL 摘要、所属合同源码摘要、after 允许公开的安全字段、实际原台账行、原 native／可执行计划、备份范围、准入及窗口引用；不保存 private before DTO、PDO 或 callable。目录／文件为受保护的 0700／0600，写入与 rename 后 fsync 仍在原锁和有效准入内。完成结果明确 `verification_level=native_same_process_lifecycle_completion`、`cross_process_preservation=not_verified`，不以返回成功冒充独立保全复验。

同一 `plugin:install`／`plugin:upgrade` 入口的 `--scope=source-development --dry-run --verify-receipt=<原native结果>` 单独只读复验原接受记录，仍须当前实际 owner／thread／session／gate 和正常原生 `pa_module_migration` 读取准入，不接受 capture／apply 参数。消费者核原受保护命名空间、owner／权限／无链接、文档完整性、原 Git commit／tree 与 writer／PLS／所属合同的真实源码字节，再核原时间有效的维护窗口、原生 dump／终态 process／RESTORE 全链、完整阶段安全字段及当前只读快照中原选定台账行。原租约现已过期不抹掉原成功；原范围外后续台账行和正常业务数据变化不与旧后态永久比较。结果明确 `verification_level=accepted_original_window_receipt`、`original_window_receipt_verified=true`、`original_private_algorithm_recomputed=false`、`current_target_verified=false`、`qualification=not_run`。旧 stdout、任意路径 JSON、缺字段旧结果或单独自算 digest 不算受验原始回执；原源码或备份引用字节变化／丢失继续拒绝。

后续正常业务可改变数据：当前目标结构／业务约束检查、原执行窗口的 before/SQL/after 保全、基于受验原始证据的跨进程复验必须分别表达。旧安全摘要不能重建私有事实；缺少所属业务复验 API 时保留拒绝，不持久化私有 DTO、不恢复临时数据库、不重放 SQL 或制造新的 preservation=true。原接受记录的只读复验不代替私有保全算法重算、当前业务终态或恢复资格。

Plugin 计划中的 `lifecycle_effects` 绑定真实生产链：begin、每条 migration/adopt、catalog 注册、失败标记分别提交，后段失败不会撤销前段；失败标记本身可能失败。单模块 catalog 同步仍包含全局 core permissions/data conditions，以及 permission、target、condition、protected resource、operation 与三类关系、menu definition、setting definition、reference-code set；还会改三张安装/归属表。操作关系可能删除后重建，菜单按全局 key 更新，不能以单租户或 `module_key` 过滤备份。该激活路径不写 settings values、reference-code entries、tenant revisions 或 role grants。File adopt 另写 module ledger 与平台审计，不能称为只补账。菜单冲突日志保留为证据，不随数据库恢复回退。

同一 Plugin 命令显式追加成对的 `--backup-tool`／`--backup-output` 时，在原生计划 consumer 内调用下述同一个选表备份适配器，直到 capture 完成仍持有原三层锁；每阶段重新读取原计划和精确 scope。它使用当前真实计划而非调用者提供的表名，不执行 Plugin SQL 或 lifecycle 写入。原生读取声明必须覆盖所有被备份共享表的完整行，另保留该原计划所需的读取声明；工具和新私有目录仍须在同一正常原生租约内。备份 payload 由完整已存表组成，原不存在表单独记录；恢复这些表的原不存在状态需要对本次实际新增对象另行批准的精确移除，不能假称 SQL dump 自动完成。

当前闭包支持 catalog/lifecycle（十四张共享表，reference-code 表可不存在）及已有 File 报告决定的四个固定 canonical 阶段：adopt 加账本和审计、image execute 加 file_object 和三张新表、references/snapshots execute 加各自新表。unify 禁止 execute，原报告继续决定 execute/adopt/reject；`FileMigrationPreservation::before(PDO,key)`／`after(PDO,privateState)` 仍是每次实际 File 写入的必要保全要求，不因类存在而从 `write_requirements` 消失。Task 的 job adoption／negative profile、Notification 的 delivery adoption／producer identity 四份固定 DDL 另按精确 key／hash 加各自真实写表及模块账本；Document base 按固定源加入六张 Document 表，barriers 只加入 document_operation，原不存在对象仍单独记录。Article67 只在精确 key／hash 且 execute 时加入 article 与 article_body_save 两张实际写表；新 save 原不存在仍单独记录，真实 Document2 前驱及 Article 内层私态保全继续作为写入要求。Member session 固定 ALTER／CREATE 也只按精确 key／hash 且 execute 加入 member 与 member_session 两表，目标缺失及所属 before／after 保全要求保持。ImportExport 固定 CREATE IF NOT EXISTS 按精确 key／hash 且 execute 加入 operation 与 row_error 两表；已有兼容表和原不存在对象分别保全，所属实际 API 仍是写入要求。各阶段继续保留所属业务合同的实际保全要求。其他待执行 SQL（包括未覆盖的 namespace 阶段）、未知 File 方向或原 hash 不符仍阻止 capture；不靠 `owned_tables` 或扫描 SQL 表名推断闭包。可见触发器仅被记录，范围外触发器写入未获准。Plugin 输出使用独立 `peanut.source-plugin-backup.v1`／`peanut.source-plugin-recovery.v1`／`peanut.source-plugin-restore-instructions.v1`，不能喂给应用 schema 的恢复消费者。`captured` 仍不是完整恢复、写入准入或资格通过。

Task／Notification 的固定阶段只由原 `PluginLifecycleService` 接入公开 `before(PDO,exactMigration)`／`after(PDO,wholeBefore)`。原生准入先保持，当前 applying 行真实提交后、原 SQL 前捕获；descriptor 只有 `module_key`／`migration_key`／`checksum`／`stageLedger`。后者是宿主固定只读闭包，绑定原 PDO／连接、请求、当前行及真实前驱，业务 before／after 的各自只读快照均调用它；完整模块账本字段必须保持，当前行仍为 applying，历史 checksum／原生 resolution 不重写，也不虚构未来 applied。原 SQL 排空后、官方唯一 applied 写入前要求同阶段 `preservation_verified=true` 和安全摘要字段；wholeBefore 含 live Closure，只保留当前回调内存，成功或失败后释放，不 serialize／hash／持久化。普通 Notification forward report 的 all-applied 约束保持，不用它替换当前 applying 阶段证明。

Notification forward 的私有回执独立于 `database.sql`。原生计划只公开固定目标路径的保护属性、原文件 hash／字节数或可证明缺失；同一包锁下的 capture 另将存在的原始 JSON 字节保存为 0600 的 `notification-forward-original.json`，并在备份前后重核原状态，manifest／恢复指引绑定该独立 payload。原缺失仅记录事实，不授权删除现有回执；恢复必须先保留真实失败 afterimage／attempt，证明本次精确文件及必要目录归属，再按明确授权恢复原字节或原缺失，不递归删除、不自动恢复或重试。rename 后目录 fsync 失败可能已有新回执，不能假定 DB 事务回滚了文件。仅有数据库选表 payload 仍不能声称回执已覆盖；新增源能力不放宽执行、资源登记、外部 writer／DDL 排除或恢复门禁。

File 四个 canonical 阶段只通过原 `PluginLifecycleService` 消费保全 API。execute 在原报告允许后、同 PDO 无外层事务时捕获；原 SQL 排空后的官方 completion 先核原报告已达 adopt 后态，再将本条 `private_state` 传入 after，要求同 key／SQL hash 的 `preservation_verified=true` 后才允许唯一 applied。adopt 在原生采用事务内捕获，原账本和平台审计写入及原报告后态核对之后、提交之前完成 after；失败只正常回滚该 DML 事务，不声称可以回滚已完成 DDL。private_state 含真实 PDO 对象，只在本条回调中持有，不 serialize、散列、记录或从公共摘要重建；成功或失败后释放。原 preflight 不额外调用该 API 扫描 File 行，已 applied 历史仍按原 resolution 合同读取，不把旧阶段摘要当作以后实时数据保全。Host、发行入口经这两条原路径消费，不创建第二执行器或新 autoload；真实备份、writer／DDL 排除、catalog／audit 恢复及现有执行／复验门禁仍独立要求。

Document 两条固定迁移通过所属模块的 `DocumentMigrationPreservation::before(PDO,key)`／`after(PDO,innerPrivateState)`，由原 PLS 实际消费。原生准入及同 PDO 无外层事务前置保持，before 后只保留内层私态；原 SQL 整份成功、结果排空后，在官方唯一 applied 前调用 after 并核 module／key／SQL hash／readonly／preservation_verified、具体 delta 和六表范围，再释放私态。base 只允许六表全不存在后原 CREATE；barriers 只追加 operation 六列和 phase CHECK，其余五表及 operation 原元数据／自增保持。观察临时将当前 SESSION information_schema_stats_expiry 设为 0，并在 finally 恢复原值；先 SHOW CREATE 初始化冷元数据，再读取真实正整数 allocator，NULL 不补 1。无外层事务合同不变，观察不启动或回滚事务。旧值保全依固定无行 DML 的原生 ADD 语义，不扫描历史正文或 operation 行，不转换旧 RichText／Article。五表 metadata preservation query 不替代此六表阶段合同或真实私有备份；本接线不开放 source apply、补造 adopted／applied、live verify 或恢复资格。

Member session 固定迁移通过原 PLS 消费 `MemberSessionMigrationPreservation::before(PDO,key)`／`after(PDO,innerPrivateState)`。原 canonical 顺序、账本和 native admission 仍由宿主负责；before 仅接受 member revision 列／CHECK 与 session 表均未出现的原态，同 PDO 无外层事务捕获内层私态。原 ALTER＋CREATE 整份成功后、官方唯一 applied 前核固定 module／key／hash／readonly、两表 delta 与保全成功，不请求时钟。既有完整 target 或 partial 均不因此获得 replay、noop 或 adopt；失败沿原生账本保留真实部分效果及原恢复点，私态在本条结束释放。旧行保全依所属固定原生 ADD 默认值及 CREATE 语义，不另扫历史会员／session 行；真实 writer 排除、精确备份恢复和来源准入仍独立要求。

ImportExport 固定阶段由模块 `ImportExportMigrationPreservation::before(PDO,key)`／`after(PDO,innerPrivateState)` 与原 PLS 配对。它按固定源核必要字段、索引、FK、enforced CHECK 及父键；已有兼容表的完整元数据、计数器和可见触发器在窗口内保持，额外自定义元数据不由本迁移改写。缺失表只由原 CREATE IF NOT EXISTS 创建，完整原 SQL 后、唯一 applied 前核两表 delta 和本次新建空表数量。历史行保全依固定 SQL 无行 DML、已有表跳过和真实 writer 排除；不扫描业务行、建立影子 schema 或把元数据摘要称为历史私态重算。目标已有不等于采用，目标缺失也不越过原 canonical 顺序／账本／来源准入；原 failed／UNKNOWN、namespace、备份工具范围及恢复权限继续独立约束。

SMS 保全复用 Notification 的公开业务证明；包含完整原行及候选组的输入只保留在执行回调内，计划仅公开安全摘要和整体摘要。源码 Host 与发行 `update-database.php` 两个直接消费者共用相同 before／after 方法，在原同 PDO 捕获本条私有输入；SMS before 严格返回 `true` 请求既有官方执行器的数据库秒／UTC 毫秒时钟，包围整份不可变 SQL 的执行及结果排空，不拆分 SQL或把批次边界称为某条 UPDATE 的精确时间。官方唯一 applied 写入前须核同 id／hash／readonly 的 `sms_reservation_verified=true`，证明同一个可行整数秒、旧列保全及新增字段后态，只公开过滤后的安全结果，随后释放私有输入。该接线不放宽当前链恢复与写入准入；安全结果不能重建私有前态，两个消费者的 SMS 独立 verify／已完成 migrate 重放均保持 `APPLICATION_SCHEMA_SMS_LIVE_REVERIFY_REQUIRED`。

源码应用的受限备份使用原入口 `migrate:run backup --scope=source-development`，必须带相同真实 owner／thread／session／gate、受保护的当前 `--plan`、已登记的 `--backup-tool` 和新建的 `--backup-output` 私有目录。原生租约必须精确包含该工具的 `tooling-resource-id` 和该目录的 `output-dir`，以及完整的数据库读取声明；原产品锁、同 PDO schema advisory lock、源码／库身份和计划摘要持续核验。缺少当前计划、登记或权限时停止，不创建新库、重装客户端或借用其他任务的管理工具。

preflight 的 `backup_scope` 只从本次 pending 的固定 SQL 取表并加入应用账本，记录原表 DDL／自增摘要、可见入出 FK 和触发器摘要。九条全部 pending 时是原有十一张受影响表；子集只取实际并集。元数据中引用的其他表不会自动变成恢复写集。schema 元数据可见性受当前账号限制，原生备份客户端另核同库直接 SELECT／TRIGGER 可见权限；备份期间必须排除受影响 DDL，不能把一致性事务当作 DDL 隔离。

原生元数据客户端在同一只读会话内先输出全部现有目标的 SHOW CREATE，再读取 I_S 分配器／FK／trigger，解析器要求带本次 nonce 的 DDL_BEFORE_STATISTICS 顺序标记；旧的统计先读输出不能取得新候选的当前观察资格。两侧仍显式使用 SESSION information_schema_stats_expiry=0 并严格比较真实分配器和 DDL 摘要，不将 NULL 补成 1。固定 [MySQL 8.4.10 InnoDB 实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.10/storage/innobase/handler/ha_innodb.cc) 的统计路径可只 peek 未初始化计数器，而 SHOW CREATE 经 handler 的 HA_STATUS_AUTO 初始化；[SHOW CREATE 实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.10/sql/sql_show.cc) 仅在计数器大于 1 时输出表级 AUTO_INCREMENT。因此新空表的 NULL／1 差异不能凭 DDL 文本相同放行；读取顺序源码、离线合同和首次冷读取的真实运行资格分记。

现有 `SourceApplicationDumpContractTest.php` 默认仅运行离线合同。显式 `--mysql --baseline=<private-json> --output=<new-private-directory> --tool=<registered-native-snapshot-tool> --owner=<real-thread>` 才运行已登记的逆向原语夹具资格：要求原生独占租约、固定源码／registry、原库 UUID 与两张既有账本的原始计数和摘要，以及可证明可见的初始对象集合。仅在原业务表不存在时创建固定夹具；两张旧账本始终只读，夹具及失败部分态保留，不使用空库清理。普通 PDO 执行生产 `restorePrefix()` 的原样载荷；原生工具仅 probe／dump。非空父行、真实 FK、CHECK、自增及断开连接前的 DML 保全结果单独记录；仅新建的 auth 夹具允许固定 block 逆向重建，父表不 DROP。这组结果不代表六条完整 Host 失败路线、迁移 runner 或 APP／生产资格通过，也不授权重放既有 applied ID。

工具登记的 `transport` 必须为既有 `ssh-docker-exec`，包含真实 `ssh_command`、`ssh_alias`、`docker_command`、`container_name`、`mysql_command`、`mysqldump_command`、`timeout_command`、`digest_command`。`source_schema_backup` 精确登记 `database_resource_id`、`database`、允许的 `tables`、`mysql_version` 与 30–600 秒的 `timeout_seconds`，不使用 schema 前缀或任意 SQL。程序只在既有容器内读取其原 `MYSQL_ROOT_PASSWORD` 给固定客户端，不向本机传递密码。调用前后核对实际 server UUID、库名、主机、端口、MySQL 版本与两个客户端二进制摘要；远端命令有原生终止期限，失败保留私有输出和本地终态回执，不自动重试。

成功调用原生 `mysqldump` 后，0700 目录保留 0600 的完整选表 `database.sql`、`backup.json`、原生进程回执、`RESTORE.json` 与 `recovery.json`。原生客户端以 InnoDB 一致性事务、逐行输出、binary hex、完整建表及 triggers 导出选定表；不带 `--databases`／`--add-drop-database`、routines、events 或表空间，不复制存储目录。普通输出只含位置、内容摘要和表清单，不含业务行。原生逻辑备份与快照限制依据 [MySQL 8.4 mysqldump 文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。

`RESTORE.json` 绑定原库、源码、对象和 payload，给出同一登记工具的 MySQL stdin 使用入口及前置条件；本入口不执行恢复。原生 SQL 包含选定表的 DROP／CREATE／数据与触发器语句，恢复须另有明确动作授权及正常原生 DDL／独占准入，先保留失败证据、核查入出 FK／触发器对范围外对象的影响，再由原 owner 在排除受影响写者的窗口内执行并核实际结构／数据。不能改成全库 restore，也不能只凭行数判定保全。`captured` 只表示真实备份输出已生成，恢复和资格仍为 `not_executed`／`not_run`；应用迁移仍受业务后态及现有单条来源字段迁移的限制。现有 recovery 引用必须匹配原生 capture 的 manifest、payload、成功进程回执及恢复说明，文件名或手写“已备份”声明不能替代这些输出。

认证 CHECK／IP 索引迁移没有行 DML，由 Identity 的公开业务证明检查必要 client 前态、原目标定义及精确目标后态。源码 Host 与发行直接消费者共用其 before／after 宿主方法，在同 PDO 的原 SQL 前后消费，仅 held callback 保留私有观察；官方 applied 前必须绑定同 id／hash／readonly 的 `target_metadata_verified=true`，只封存安全成功字段和目标元数据摘要。Auth 不请求 SQL 时钟，不扫描令牌或事件原行，不因无关自定义列或触发器拒绝；两条 DDL 之间仍保留实际失败与恢复边界。独立 verify 复用既有 Auth 目标元数据比较，不能把它解释成历史业务行保全。

File 四条 canonical adoption 目标若按既有证明选择执行原 SQL，官方执行器在标记 applied 前再次调用原 File 证明，必须观察到完整后态并返回 adopt；证明失败保留 failed 事实。此检查覆盖原证明的结构与数据不变量，逐原行保全、触发器影响及恢复范围仍须由实际迁移合同和维护窗口覆盖。

Identity 首次源码安装的九条固定迁移另有窄恢复合同，仍使用上述原生捕获、客户端和产品／schema／package 锁。带 backup 的原计划封存 `identity_recovery_preflight`：固定逆向程序、原生执行器和业务证明源码摘要，以及范围外父表引用的 PK／FK 绑定摘要；原备份还须通过固定 inverse 的原件解析。实际 apply 在写入前重验这些输入。它只证明本次源码恢复合同可消费原件，不代表实际 MySQL 恢复或发行资格已经通过。

`plugin:install official.identity --scope=source-development --dry-run --snapshot-operation=<原native操作结果>` 保全一次真实安装的后像，另需真实 actor 字段、`--metadata-tool`、`--backup-tool` 和新 `--backup-output`。原结果可以是完成或失败；目录／文件来源、原生产者 Git 字节、固定 SQL／包、原准入／窗口／备份／阶段回执均须成立，不把 catalog 阶段失败伪造成 failed migration。输出 `peanut.source-identity-operation-snapshot.v1`；它不是前态备份，不能作为下一次 apply 的 recovery。失败账本原观察为 UNKNOWN 时可保全，自动恢复仍拒绝。

`plugin:install official.identity --scope=source-development --restore-operation=<上述capsule的backup.json> --maintenance=<本次窗口> --metadata-tool=<登记ID> --backup-tool=<登记ID> --backup-output=<新目录>` 是独立的显式恢复，不带 dry-run、source-plan、recovery 或 verify-receipt。窗口使用 `peanut.source-identity-maintenance.v1`，绑定当前 source/database/authority/registry、`operation=restore_identity_operation`、精确 `operation_capsule` 路径／摘要、固定 affected scope、有效期和实际排除 HTTP／workers／other-writers 的原始回执。当前 owner 使用自己的新原生 DDL／exclusive 准入；历史 writer 身份不继承权限。真实完成操作也可在尚未开放业务写入的受控窗口内明确逆转并保全其完成事实，不能制造失败来取得恢复资格。 同一命令增加 --dry-run 时只返回持锁恢复计划和证据，实时能力不授予原生 SQL 写入；计划明确 fresh-before 仍须在实际恢复时捕获并逐字节核对，不能把计划当作恢复已执行。

正常逆向只移除原本缺失、本次 owner after 已接受、当前元数据摘要相同且仍为空的六张表，按逆 FK 顺序执行；缺少 accepted 后态默认停止。唯一首条 policy CREATE 失败可使用独立的 peanut.source-identity-first-create-recovery-proof.v1：原 old_ledger 和 accepted stages 均为空，当前只有固定首 key／checksum 的真实 failed，其他五个 CREATE 目标仍缺失；当前窗口的 failed_first_create_metadata 路径／摘要必须引用原 SQL 后回调的原生 request。原 binding／nonce／tool／adapter Git 字节、终态／输出摘要／字节及完整 DDL 均核实，原备份→迁移开始→request→受保护终态文件 mtime→failed 账本结束→原失败回执按原历史窗口闭合；文件 mtime 不是新增的原进程时钟证明。原业务／目录表的 dump 块仅忽略解析器已确认首条 DROP 语句前的原生分隔空白，其余 SQL 字节须完全一致，不归一语句内部或数据值；仅实际首阶段账本及对应安装状态可变化；原生完整 DDL 与 capsule／当前图相同、policy 为空且真实 allocator 仅 NULL／1，外部绑定／FK／trigger 继续核验。窄历史 reader 显式使用已核旧 producer 的实际输出顺序，只返回历史失败证据，不升级为新格式完整 metadata 资格，也不补写旧 safe_after；实际恢复仍必须通过全图 fresh-before／after。department／audit 只逆固定新增索引／列，原列、原行及 allocator 必须保持。共享 catalog 和安装／迁移表保留原 PK，以原件标量字面量恢复；仅 operation_permission 的原关系 ID 允许因正常删除重建而缺失，先移除替代行再插回原 ID。未知自然唯一键改写、原父身份缺失、范围外依赖、trigger、CASCADE／SET NULL 或未声明派生写均拒绝。condition 的 STORED 生成值不进入恢复 DML，选表 dump 仅接受其原顺序可写列清单；该格式依据固定 [MySQL 8.4.10 mysqldump 实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.10/client/mysqldump.cc)，离线解析不替代非空生成列的真实恢复。

写前的六张范围外引用表 PK／FK 摘要随真实完成／失败回执保留；完成前重读比较，snapshot 和 restore 再消费原摘要。失败后有差异仍可取证，但不能取得恢复资格；captured guard 持续重验这些绑定。原备份、操作回执和 capsule 必须始终位于原先登记的连续停写窗口内；窗口过期后的 snapshot 仅能取证，`recovery_eligible=false`，不能事后补声明取得恢复资格。读取原件、窗口、操作回执及全部原生终态／输出时，以同一次受保护读取固定解析与摘要，并在后续 guard 重验完整来源链。恢复前持锁重新捕获 fresh-before，完整原生字节须等于 capsule；随后才从原件／capsule 派生并以受保护摘要 stdin 进入同一原生 mysql，FK／unique 始终开启、禁止 reconnect。原生写入期限取本次维护窗口和租约较早者，启动须留出 timeout＋60 秒。DML 有事务，表移除、ADD 逆向和 allocator DDL 不是整体原子操作；中断保留阶段／终态和真实部分态，先对账、不自动重放。只有完整 postimage 等于原件、原 absence 恢复且范围外绑定未变，才封存 `peanut.source-identity-operation-restoration.v1`。该结果仍明确业务数据库和产品资格未验证，不自动重装、发行或开放写入。
