# 事件、任务与异步协作机制

生效设计，具体 schema、驱动和参数由实际模块合同固定。同步服务、框架事件和持久任务分别使用，不根据空事件文件或类名推断可靠总线已经完成。

## 1. 语义

Command=请完成业务（如预留库存，可普通方法）；Job=指定处理者稍后工作（导出）；Event=事实已发生（订单已创建，可多个订阅者）。事件不天然异步；付款/扣库存需要结果时不能只发事件就报成功。改变决策的同步扩展点须有明确输入输出，不冒充事实通知。

## 2. 事件登记

稳定 ID、中文名、发布模块/格式版本、发生条件/事务提交时机、字段/敏感规则/租户、接收者/同步或异步、可靠性/顺序/防重复/失败去向/弃用。代码归模块，目录统一生成。

例 `order.created`：订单模块保证成功提交事实；仅订单号/租户/必要摘要，无 Token/密码；通知和统计异步处理，同事件不重复产生业务效果，失败重试或人工入口。事件 ID 是示意，不是已定新 schema。

## 3. 可靠投递

需要不丢的后续工作：业务结果＋待发送记录同一实际事务提交 → 后台读取登记类型 → 投递事件号/租户/版本 → 接收方验权限/防重复 → 执行并记录状态。采用现有持久任务/Outbox，不默认大型中间件或所有调用异步化。

至少一次投递由接收方按事件＋处理者防重；外部渠道还需幂等键/回执/未知结果查询，不能凭本地已处理标记承诺恰好一次。顺序按业务键，不承诺全局有序；未知类型/版本拒绝或隔离。只在提交成立后对外发布最终成功，数据库回滚不能撤外部付款/短信。

## 4. 同步钩子

声明异常是否传播、是否加入当前事务、能否改变结果；输入/事务内/提交后钩子分别命名。模块停用/升级、撤权、代码缺失时处理在途工作的策略明确，不无限重试；格式兼容窗口随版本矩阵维护。启用钩子有外部动作时须幂等/补偿，不能依赖 DB 回滚。

## 5. 任务

登记类型、处理者、输入、租户、实际身份/授权来源、状态、重试/防重复/取消/超时/并发/进度、结果和人工处理。管理端只提交登记任务/合法输入，不接任意 Shell、类名、路径或 DB 连接；不保存长期用户 Token，不沿用上一任务状态。

统一领取/租约续期/超时回收；失租不再产生新副作用，必要时执行版本阻挡旧持有者。授权在开始、提交批次、结果交付前复核，Scope/模块停用同步生效；checkpoint 须位于实际批次/副作用边界，不是拦截任意代码的沙箱。结果下载也授权。重试/并发/租约参数有业务依据，不能只调大超时掩盖执行缺口。

## 6. 完整例子

订单与库存预留在确定的一致性方案内完成，事务内记必要待发事实，提交后通知/统计。短信失败不把已成立订单改成创建失败；入队也不等于订单完成。

采购收货：验证身份/仓库参数→核单据及动作/仓库权限→调用库存公开入库（数量/并发/防重）→同事务保存收货结果和需要的待发送事件→提交→通知/统计。异步入库先显示处理中，确认结果才完成；跨库另定一致性，不假称同库原子。

## 7. 诊断和验收

开发者中心展示发布/订阅、格式/源码/文档、处理者/依赖、脱敏失败/重试状态。重放有独立授权及外部副作用提示。

测提交前失败不外发、提交后暂时失败可恢复、重复/并发、错租户、撤权、未知版本、模块停用、代码缺失及外部未知结果。通用 Outbox/事件闭环未验证不得报成熟。
