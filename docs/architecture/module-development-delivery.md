### 作者源码与宿主验收源码必须分开

官方 Module 的新功能、迁移、版本、Composer 声明和公开制品，只在模块开发专用应用作为**唯一作者源**维护和发行。Code 负责宿主装配、创建、升级和真实消费者验证；ST/MT 公开薄模板默认不附带 Module 作者源码，业务 APP 依据实际需求选择模块及其依赖闭包。

**2026-11-12 迁移现场**：Code 开发仓仍保留 8 份历史官方模块源码，供本仓 server/composer.json 中的 8 个 path repository / Composer require 与宿主验证使用，现存 77 个服务端测试文件和若干工具直接引用路径；其中 File、Identity、Ops、ReferenceCodes 版本落后于模块专用应用。此为**尚未迁出的宿主兼容测试输入**，不是并行开发/发行权。不要从 Code 旧副本更新官方模块版本、打新包或覆盖模块开发应用源码，也不要以删除目录代替消费者迁移。

后续退出分两步：先把真实 Module 业务测试迁到其作者应用，Code 仅保留最小宿主装配/升级契约；再为 Code 开发期测试配置独立、可信且不依赖维护者本机绝对路径的模块消费输入，按 Composer/锁及直接 HTTP/Module 生命周期定向验收后，才能删除 Code 旧目录和 path repository。任何阶段不得让已安装业务 APP 降版或清理其租户数据。

## 1. 模块逻辑统一，源码前后端分开

后端代码在后端工程，运营/租户后台/前台/应用代码各在对应客户端，以同一模块编号汇集发布。可只有后端或部分页面；不强迫前后端同目录，后端不依赖 Vue。构建登记、运行懒加载与远程热加载分开；改源码重建受影响网站/App/小程序，不承诺免构建。

下游专属规则默认进入应用自己的 Module，不为了业务便利直接改技术 Core 或公共脚手架。可复用功能优先完善所属能力模块；无业务属性的技术机制或确实缺少的宿主扩展入口才归对应 Core/脚手架，不能因为“可复用”就一律下沉 Core。模块化首先减少上游升级时的文件级冲突，不承诺业务代码永远免升级：公开类、方法、事件或数据合同变化时，真实消费者仍须按兼容要求适配。

### 1.1 能力模块的三种使用形态 {#capability-forms}

能力模块是一项边界清楚、可复用且可扩展的功能单元，不以菜单、页面数量或是否构成完整应用划界。按实际需求支持以下一种或多种形态，不强制每个模块全部具备：

| 形态 | 使用方式 | 交付与验收要求 |
| --- | --- | --- |
| 独立功能应用 | 用户通过模块自身的页面完成一项完整工作 | 依赖和权限满足时，页面、实际操作及结果可用；无需另造一套底层实现 |
| 能力或组件提供者 | 其他模块通过公开服务、SDK、hooks、provider 或 UI 组件使用能力 | 明确调用/输入输出、扩展、依赖及失败边界；可以没有菜单、页面或自有数据库 |
| 两者兼备 | 自有操作界面可用，同时公开部分能力或组件供其他模块、应用复用 | 自有页面、嵌入组件及接口适配共用同一核心实现与业务规则，不复制成独立版/嵌入版/接口版 |

“独立”指工作入口和功能责任独立，不承诺脱离脚手架、Identity、File等已声明依赖运行。“外部可调用”须区分包/组件导出、同进程公开调用和远程 API；按真实消费者选择，不强制所有模块拆微服务或把内部服务暴露到公网。单独部署、跨实例授权和远程调用只在确有需求时沿已有合同实现，不由本节自动开启。

### 1.2 同一能力，不同入口

有页面的模块，其自有页面也应消费本模块公开能力，不能另藏一份只有自有页面可用的业务规则。复用既有服务/组件和原生装配即可，不为每个函数增加接口、SDK或转发层；不强制同进程调用绕行 HTTP。页面与嵌入组件可按宿主提供导航、布局、选择范围或事件处理，但不能改变服务端授权和业务不变量。

以工作流为例，目标是同一流程能力既可提供独立设计/办理页面，也可按需求把设计器或办理组件嵌入其他模块，还可仅通过公开服务发起/查询流程。新闻审批规则由新闻模块组合，流程执行和可复用组件由工作流负责；不得分别维护三套审批逻辑。此例是职责与目标，不宣称当前所有形态均已实现或验收。

“有哪些能力”“采用哪种入口”“如何打包部署”分别描述。一个能力可有多种入口；目前实际所有模块均按一个 Module 对应一个独立安装单元，应用通过依赖与锁选择多个模块，不需要再把它们复制成多模块物理 Bundle。按真实业务需要组合功能时，使用现有模块依赖或应用选择，不为每个入口建立重复模块、数据模型或另一套 manifest。验收只覆盖声明支持的形态：纯能力模块用真实消费者证明可用；兼有页面与嵌入入口时核对两者规则和状态一致。前端隐藏不代替后端授权，包导出不授予数据访问权。

安装制品与其 Module 使用同一个 key 和业务版本；`module.json` 是唯一作者源声明，`modules.lock` 由该声明、实际源码与 Composer/npm 原生声明派生，不再另写 `plugin.json`。单 Module 归档直接携带该 Module 的源声明及其拥有的源码；不提供多 Module 物理 Bundle。应用组合沿现有依赖图与锁选择。Composer 包、npm 包和各客户端包保留各自原生版本，不强制等于 Module 业务版本。

`module_installation` 是唯一安装实体，保留 Module ID、已安装版本、运行状态、制品/依赖身份和恢复字段。停用的 maintenance 状态不因发布选择或新版源码出现而变为 active；正常卸载保留该行历史、原生迁移记录和业务数据，明确 purge 才进入受控清除。第三方 Composer、Vite、编辑器等生态的 Plugin 概念不受此约束。

已有应用通过原生脚手架升级计划完成一次性声明转换：验证原应用完整 `plugins.lock` 及包装摘要，将其全部选择（包括应用自有 Module）派生为 `modules.lock`，将旧锁及全部已验证包装的删除列入同一备份/应用/恢复写集，再允许新运行入口加载。不能直接覆盖成脚手架默认模块集，也不能要求应用手删锁或重装。旧安装账本沿原生前向 Migration 归并；应用的数据与恢复边界见[原目录更新说明](../public/application-release.md#4-已有生产原目录更新)。维护者迁移细节见 Code 源码仓的 `docs/maintenance/migration-protocols.md`，不随生成 APP 交付。


### 1.3 业务驱动完善，应用按固定基线采用 {#capability-evolution}

开发时先复用现有能力；发现缺口后确认是调用接线未完成、应用专属规则、所属模块能力不足，还是底座扩展机制缺失。只在正确源头修复，先改原生配置或已有扩展点；不能把误用当底座缺陷，也不为尚无消费者的设想建万能框架。

公共增量完成直接必要检查后，固定本批源码/版本/锁及对应制品，由应用按原生模块或脚手架升级入口采用，并确认依赖它的真实业务。只改一个模块不强制重发整个脚手架；开发候选、固定发行版本和生产采用分别处理。应用不跟随浮动dev或每次提交自动升级，也不必等底座所有未来能力齐全才开发业务；等待依赖的部分明确标记，其他无冲突工作继续。

联合开发阶段可显式使用本地 Core 与模块源码，不为每次修改先正式发行。正式采用按依赖顺序：有变化的 Core 发行 → 脚手架采用并发行 → 模块生产应用升级脚手架、收敛模块并独立发行 → 消费应用先升级脚手架、再升级实际使用模块。模块生产应用自己的模块保持作者源码，不以消费同一制品覆盖回来；发行前确认最终正式依赖组合。每批先收敛依赖与模块锁，再原生派生和必要构建，不逐模块重复全套准备。源码仓中的 CI 完整测试参数只控制 CI，不自动启动本地测试；实际参数见维护者的 Core 发行文档，模块自身自动发行能力须核实际入口，不能由流程约定推断已实现。

确需先在应用落临时公共补丁时，沿原任务记录精确路径/提交、原因、所属上游、取代条件与消费者。上游接收后应用采用对应版本并移除已被替代的补丁，不能长期保留两份实现。升级冲突按应用定制、已提前采用的上游修复、组合依赖、生成物及真实扩展缺口分别归因；不能一律覆盖、保留、扩大app-owned或修改摘要来消除提示。

一次缺口的闭合既包括上游能力交付，也包括原应用改用公开能力且保留原业务结果；受管文件上的同类定制应不再重复。下一次真实升级检查是否复发，而非为了证明零冲突再造一次无意义升级。文档定义不会自动使未实现的扩展、检查器或运行行为成立。

## 2. 模块登记

编号/中文名/版本/功能/来源、依赖、后端/各端入口、公开服务/权限/配置/事件/任务、表/文件/缓存/其他资源归属、迁移/生命周期/兼容、多语言/审计均登记。完整字段职责见[总览 §4](overview.md#4-模块基础能力)。源码定义唯一；安装、开通、角色状态各由运行记录提供，不维护第二模块定义。

### 可信代码与执行边界

只安装经过审阅的可信 PHP 模块，核对来源、许可、依赖和行为。进程内插件不是安全沙箱；普通租户不能上传并执行服务器代码。Module 是唯一功能和交付身份；这里的进程内插件泛指扩展代码，不是另一层可独立定价/安装的对象。不按每个内部函数机械拆模块，也不另造一套安装、依赖或版本登记。

Provider 和各端贡献沿正式框架入口装配，冲突在编译/登记时明确拒绝，不按加载顺序静默覆盖。提供者由产品明确选择，不在请求期间猜测；必需模块不能任意停用。新入口停止、在途任务、客户端贡献退出、资源保留和卸载是不同动作，按既有生命周期及下文依赖约束分别处理。元数据格式变化需要版本和迁移，不新增竞争 manifest。

原生模块 Service 的 register/boot、事件/路由/命令，统一按[框架扩展与生命周期](framework-extension-and-lifecycle.md)接入。启动扩展不是安装/迁移，也不授予业务运行许可；租户权益按当前套餐与许可证判断，不再提供逐模块租户启停钩子。

## 3. 模块之间怎样调用

| 方式 | 合同 |
| --- | --- |
| Query | 只问结果，不偷偷改业务状态 |
| Command | 完成明确业务并返回结果，普通服务方法即可，不等于 Shell/消息总线 |
| Event | 宣布事实，声明同步/异步、时机和失败语义 |
| Job | 指定处理者延后执行，定义授权/重试 |
| Projection | 预计算只读结果，标新鲜度，不反写原业务 |

公开方法表达预留库存/取消订单等业务，不一律万能 save；公开类不强制 interface，接口用于真实替换/边界。稳定跨模块结果不泄露 ORM/表名/HTTP Request；不调内部 Controller、不以字符串猜类绕登记。写入必须经过数据所属模块的业务入口，内部调用不天然可信。

业务 Module 调用 Peanut Kernel/Core 时同样只依赖明确的公共能力，不把 Core 内部实现当稳定 API。若现有公共能力不足，先补可复用的扩展入口或公开契约，再由业务 Module 消费；不要以直接修改 Core 内部类来完成单一业务需求。

当前敏捷开发阶段，同库模块允许使用ThinkPHP ORM模型关系（包括belongsTo、预加载及JOIN）进行只读关联，不强制额外建立View、公共ReadModel或独立Query Service。必须保持tenant隔离，主记录/关联记录按同一获准tenant限定；只取得业务实际需要的字段，禁止通配暴露来源模块密码、密钥等敏感数据。关系只用于读取，调用方不得据此save/update/delete来源模块数据，也不得把可写ORM对象暴露为外部接口结果。

跨模块筛选、统计、计数、稳定排序、数据库分页和导出在数据库内完成，不以逐条查询或全量ID/内存分页代替。使用模型关系时明确软删除、缺失关联和历史语义；不能因引入默认Scope而静默改变历史订单关联。Payment现有会员JOIN保留tenant等值约束和原INNER JOIN语义，仅读avatar/nickname/account等实际展示字段，其他会员字段仅按既有筛选需求使用。关系写入、库存预留、扣款等业务动作仍调用所属模块命令。后续只有依赖明显扩大、来源模块需要独立演进或拆分时，才评估公共读取层。

订单例：商品公开查询并保留快照→库存原子预留→返回预留号/失败→订单关联，由用例协调同连接事务。查有库存不等于预留成功；调用者不能自己改库存表，参与模块不能擅自提交一半结果。外部支付不受本地回滚，跨库/远程另有状态/补偿/核对。

### 现行批量查询与回调引用示例

Identity 的 `AdminDirectoryQuery::activeTenantIds` 只为调用方已选定的编号返回生命周期，`memberDisplayNames` 只返回指定租户既有日志引用的当前姓名；两者都不授予业务权限。调用方先限制自己的读取范围，使用有界批次，不能把全部记录加载到内存后再筛选分页；当前姓名不能冒充审计当时的历史快照。

Payment 使用 Integration 公开的 `ExternalTenantResolutionService::bindingForGrant` 核对渠道归属；未找到返回 null，歧义或错归属拒绝，停用状态由原授予/配置用例分别判断。需要锁时保持租户先于绑定的顺序，加入调用方事务，不在查询中提交。

OAuth 从自己保存的 state/ticket 读取引用后调用 `bindingForCallbackReference`；它返回未认证的绑定候选，不是授权成功。仍须调用 `verifiedCandidates` 并完成 OAuth 一次性、有效期和渠道验证。缺失、孤立或歧义引用明确失败，不能过滤掉坏候选后把剩余一项当作唯一合法归属；原始密钥和票据不进入日志。

### 宿主与扩展提供者使用公开入口

设置宿主消费已登记的 `TenantApplicationSettings`，由 Settings Provider 将接口绑定到所属实现；宿主的容器工厂同样请求该接口，不直接绑定内部 `TenantApplicationSettingService`。调用合同改变不代替既有租户上下文、权限和业务校验，也不为同一个能力再建转发层。

网站配置使用已登记的 `Service\WebsiteConfigService`：`get/save` 仍处理可信租户上下文、固定字段与文件引用，`defaults` 只返回模板默认值，不读租户状态或授予权限。公开业务类可由原生容器装配，无须仅为命名再加一层接口。`OAuthBrowserCallbackService` 只提供既定浏览器回调地址和允许的查询参数，不能把回调跳转当作身份验证。

导出授权资源使用公开 `ImportExportCommands::RESOURCE_KEY`；固定值仍为 `peanut.import-export`，宿主不为读取标识而依赖内部任务编排服务。标识、公开类型与真正获得授权是三件事，原授权核验及一次性消费不变。

导入导出扩展实现已登记的 `Engine\Contract\DataProvider`，配套使用 `ColumnDefinition`、`SchemaDefinition`、`ExportBatch`、`RowIssue` 和 `ImportExportException`。提交与查询用例的 `AsyncExportOperation`、`CsvExportOperation` 也是公开结果/输入类型；它们不是存储记录或授权凭据。提供者只处理自身数据，导出批次上限500行，导入列/导出列、模式修订、游标和错误码保持原合同；日志提供者仍拒绝导入。执行前依然由原用例/worker验证授权，不因为类型公开就允许未授权直接执行。存储库、任务编排实现和数据库查询对象不在此公开面内。

Ops 的平台业务入口及其 `MaintenanceWindow`、`OpsStatusSnapshot`、`OpsTask` 结果、稳定异常和租户诊断字段已显式登记；结果公开不授予平台操作权限。`BackupRestoreProvider` 与现有 `PairedBackupProvider` 仅定义逻辑提供者/处理者/隔离目标及重试上限，后者不执行备份、恢复或任意命令；它不是持久化对象。真正的任务存储、数据库执行器、恢复验证与部署资源仍保持内部边界和各自执行授权，不能因为描述器可见就绕过它们。

部署目录协作通过 `ReferenceCodeCatalogService` 处理已选定、编译过的模块贡献：只同步所选模块，未选择的定义保持不变；无存储且无贡献可为空，实际声明贡献却缺少存储必须拒绝。目录修订返回固定定义字段和计数，不返回租户字典条目或查询构造器。宿主保留原生命周期授权、依赖检查和外层事务；公开此协作入口不授权任意安装、停用或删除。来源文件必须位于声明模块根内，普通用户输入不能充当已批准模块清单。

设置目录通过 `SettingCatalogService` 加载并同步同一批已选模块，内部复用原JSON Schema、秘密默认值限制和修订同步器；目录移除只退休定义，不删除或覆盖部署、租户、对象设置值。宿主通过固定目录字段与计数计算原有修订指纹，不直接查询设置定义表，也不能用目录入口替代运行时设置授权。目录清理、权限失效和真正的数据删除仍是独立生命周期操作，不因同步成功而自动放行。

Identity 目录复用已公开的 `ModuleAuthorizationCatalogSynchronizer` 和 `MenuCatalogSynchronizer` 提供固定定义摘要、活动计数；前者负责目录变化后的授权修订失效。模块选择与外层事务保持，空选择不修改任何租户；Core、基础模块和共享 API 目录变化在实际写者事务内推进全部租户授权修订，覆盖没有套餐模块选择行的租户。组合操作由外层统一失效，失效不授予权限或开通模块。部署宿主不直接读写 Identity 私表，公开同步器也不意味着获准执行生命周期操作。

## 4. 依赖是业务成立的前提

必需项缺失拒绝；可选项缺失有真实退化；可替换能力由产品明确选提供者并记录，不临时猜。依赖无环，安装/开通/升级/停用/卸载均核适用版本与状态。

例（箭头为左依赖右）：订单→商品/库存；收款结算→订单/支付；库存→商品资料。仅为实物交易例，不固定所有行业；收款结算不自动等于会计/供应商结算/资金清算。

代码/服务依赖≠租户业务开通依赖。订单明确要求当前租户开商品/库存时必须满足；汇总调用库存读服务不迫使接收方开入出库。来源模块状态及数据共享另核，不能以代码存在绕过业务开通。

## 5. 受众入口

平台（运营，非默认租户业务权）、租户员工、用户/访客、合作方（关系授权，可 API 分组）、外部回调（绑定/签名/防重）、系统 CLI/worker。用 ThinkPHP 多应用/路由等入口适配同一业务实现，不六套服务，不随结构整理破坏现有 URL。

## 6. 打包与分发

UI/CLI 共用服务：固定源码/版本→读取登记路径/各端贡献→预览来源/目标/用途→校依赖、路径、秘密→按交付类型构建/收集→输出清单/版本/摘要/来源/文档→核包→在获准渠道发布。包生成不是发布。

规范化绝对/父目录/符号链接边界并查覆盖冲突；不任意扫磁盘。源码不含 vendor/node_modules、缓存、真实环境秘密、客户数据或原始日志；正式交付制品可含批准构建产物。采用 canonical manifest/lock、确定性 tar 和受管清单；同发布身份不改内容，未实现签名不报已签。

## 7. 安装、升级、开通、授权分别处理

| 动作 | 不自动获得的能力 |
| --- | --- |
| 源码发现 | 不代表安装/运行 |
| 包安装 | 不给所有租户开通 |
| 租户开通 | 不给所有人员授权 |
| 人员授权 | 不绕模块/租户/对象状态 |
| 数据范围授权 | 不自动安装/开通来源模块或获其写权 |
| 停用 | 不删数据；定义新入口/在途任务和贡献退出 |
| 升级 | 不覆盖客户代码/秘密 |
| 卸载/清理 | 退出代码与删除数据分别批准，活动依赖和引用须检查 |

安装升级：先预检/计划/备份，再迁移/前端处理/健康验证；失败保留现场并按可验证步骤恢复。不可逆数据/外部副作用不因还原源码而回滚；框架安装服务、向导和 CLI 共用逻辑，不覆盖未知旧库。源码升级计划同时检查保留的客户 Module 对目标 Module Kernel 的版本约束，以及可静态确定的 Kernel 类/静态方法引用；发现不兼容时在 plan 阶段报告 Module、文件和行号并阻断 apply，由开发者或 Codex 修正业务 Module 后重新 plan。该检查不自动改业务代码，也不冒充完整运行/行为兼容证明。租户无固定类型，集团暂缓且只能授权读取 Scope。

## 7.1 脚手架随附模块的局部定制与整体升级

原生 scaffold upgrade 先验证 APP 的完整模块归属和实际保存的上游基线，再作逐文件三方比较。对于普通受管源码，只有初始分类为 `preserve / project_modified_only`、当前内容不同于基线、目标内容仍等于基线、源文件 mode 未变时，才允许保留该文件定制并升级模块其余源码。登记文件的实际摘要可能早于本地修改；当前摘要必须重新读取，不能靠重写登记或把当前定制冒充上游基线取得升级资格。缺失旧源码、未知来源、归属变化、本地新增/删除/重命名、双方修改或 mode 变化均不由这个例外获得替换权。

例外不涵盖模块声明、Composer/npm 声明与锁、各端贡献入口、旧/目标模块声明引用的 backend 装配资源与迁移/seed 目录，以及 `generated`、`metadata`、`META-INF` 下的派生身份；`generated-managed` 文件也不适用。声明引用按真实路径保护，不假定固定在 `resources` 目录。目标上游新增或删除未定制源码仍走原有完整模块投影规则，不据此合并真正冲突。

计划的 `plugin_target.managed_upstream_proofs.<module>.preserved_overrides` 记录保留路径、当前及基线摘要与 mode，并计入归属摘要。暂存区先渲染整个目标模块，再复制这些已绑定的定制文件；复制前后复核实际文件、真实基线与暂存文件，随后沿用原生 make/lock、完整模块图及依赖检查。模块声明和版本来自目标上游；`modules.lock` 按完整实际投影派生，不能把混合源码冒充未定制发行包。

apply 仍按原始 preserve 动作保留当前文件，并把目标上游字节写入下一版 baseline：APP 实际摘要与 baseline 摘要分别记录。baseline 副本物理 mode 固定为 `0644`，原源码 mode 单独保存。后续上游改到该定制文件时，仍须重新判定三方冲突；本例外不扩展冲突解决、apply/verify 或恢复权限，也不替代真实升级后的业务验收。
